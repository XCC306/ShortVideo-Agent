# 05 工程复盘

本文件由实际开发与验证记录归纳，不替候选人编造个人主观感受。候选人提交前应核对这些事实，并补充或修订为自己能解释的认识。

## 1. 最难的问题

最难点是让真实模型在严格事实约束下完成动态闭环，而不是只返回一段看似合理的脚本。
第一次真实请求中，模型多次检索却始终得到空结果，原因是检索器把整段中文作为一个词。修复后，又暴露事实只写在 Claim 而没出现在实际旁白/字幕中的问题。最后一次检查通过后还需要一次模型完成响应，原 8 次请求预算不足。

这些问题分别属于检索工具、模型提示和运行控制。若都归因为 Python 环境或直接放松规则，会掩盖真正原因。最终通过 Trace 区分问题、修正中文匹配与写作约束、保留验收门槛并把请求上限调到 10，才取得真实完成记录。

## 2. 过程中的取舍

单 Agent、三个本地工具、标准库 HTTP 和 JSON 足以展示题目核心，未引入前端、向量库、数据库或多 Agent。
事实采用精确原子文本，牺牲自由改写能力以得到可复现的证据校验；副作用是最终演示偏短、偏保守。15 秒单镜头只有一句旁白，工程通过不能等同于内容质量充分。
受控模型便于覆盖失败、预算和旧版本检查，但无法证明真实模型会如何决策，因此保留了两组独立真实 Qwen 证据。

## 3. 从本次工程可归纳的学习点

- 环境能启动、API 能返回、工具能命中、脚本能通过检查，是不同层次的条件，应按 Trace 定位，避免反复重建环境。
- 同一最新草稿的实际工具结果才有验收意义；模型口头说“检查通过”不能代替执行证据。
- 故障验证应实际执行并标明注入方式；离线替身不能冒充真实模型能力。
- 交付规范应在开始时核对。早期权限迁移、过细文档和重复清理占用了过多时间，后期才发现必须提交 GitHub 项目及三组材料，造成返工。
- AI 可加快实现，也需要明确披露其贡献，并由候选人亲自理解、选择与验证；不能把自动执行写成个人手工完成。

## 4. 下一步（本次未实施）

优先改善多分镜脚本的实用性和表达质量，并用小规模重复真实运行评估成功率与预算；随后提高中文检索排序、事实覆盖和工具异常分类的准确性。
这些是可继续的改进方向，不是已实现功能。本次不扩大到前端或云部署。
